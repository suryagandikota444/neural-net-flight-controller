**Read the project in the order that data travels, then revisit it in execution order.** The root is bare-metal C firmware; `fc-nn/` is the Python training/simulation workspace. The dated review directory contains diagnostic artifacts from the repository review, not the production controller.

For your first pass through any file, read its public functions and constants, sketch its dependencies, and ignore long explanations until you have identified the executed statements. This repository has unusually extensive comments, but several comments describe older behavior. Your second pass should compare the comments to the actual implementation. Your third pass should reproduce one calculation or behavior with a test.

**1. Start with [fc-nn/main.py](../../fc-nn/main.py), which explains how the Python tools are reached.** It dispatches `train`, `view`, `validate`, and `export` to other modules. It does not implement physics or neural inference. Understand how it modifies `sys.argv`, how each subcommand parses arguments, and how the current working directory affects model/output paths. Run `main.py` with no command to read the dispatcher help; run individual subcommands with `--help` after their dependencies import.

Write down that `main.py export ...` defaults to a file named `weights.h` in the current directory. From `fc-nn`, that is not the root header compiled by firmware. The eventual export destination must be explicit. This small path detail can invalidate an otherwise correct deployment experiment.

**2. Read [quadrotor.xml](../../fc-nn/quadrotor.xml) as an executable physical specification.** Mark each body, joint, inertial element, geom, site, actuator and sensor. A body describes a coordinate frame and attached mass; a free joint gives the aircraft six degrees of freedom; an inertial element gives mass, CoG and inertia; a geom may participate in collision and inferred inertia; a site marks a force/sensor location. An actuator's site and gear determine the force it applies. A pretty motor cylinder is not a spinning rotor model.

Draw the hierarchy: world → drone → four fixed motor bodies. The target ghost is a separate mocap body, not flying payload. Annotate the central-body mass and each child mass. Record which geoms collide, which are visual only, and whether the physical contact shape resembles the actual landing supports. Note the propellers are visual cylinders without modeled rotor inertia/spin DOFs.

The XML actuator gears begin with unit Z force; Python rewrites the Z gear to per-motor maximum thrust. Yaw reaction torque is applied separately by Python. There is no actuator-level motor time constant here. The apparent smoothness currently comes from controller action filtering, which is a different mechanism.

Read the [MuJoCo sensor reference](https://mujoco.readthedocs.io/en/3.5.0/XMLreference.html#sensor-accelerometer) to confirm sensor frames: accelerometer and gyro readings are expressed in their site's local coordinates. Distinguish those readings from world-frame position/velocity signals used for reward and diagnostics.

**3. Read [drone_env.py](../../fc-nn/drone_env.py) in five pieces.** First inventory constants: gravity, integration timestep, frameskip, episode duration, aircraft parameters, action scales, observation scales, noise, termination and curriculum limits. For each, mark whether it is physics, measurement, controller behavior, or task definition. Those categories should not share unexplained “tuning” changes.

Then inspect `__init__`: it loads MuJoCo, caches object IDs, declares 12-dimensional observations and four actions, initializes the viewer lazily, and allocates episode/controller state. Understand why using named IDs is preferable to relying on accidental XML indices. Check that every cached sensor slice uses `sensor_adr` correctly.

Then inspect `reset`: it seeds an environment RNG, samples aircraft parameters, resets MuJoCo, edits model parameters, samples tilt and commands, places the aircraft at commanded altitude, forwards the model, and clears action history. Make a reset-state checklist. Later compare the custom reset in `validate.py`; it fails to reset everything the training environment resets. Also ask whether editing a model field actually changes derived physics: the current CoG issue demonstrates why assignment alone is insufficient evidence.

Then inspect `step`: raw actions are clipped; a stateful EMA smooths them; hover offset and action scale produce motor commands; commands drive thrust; yaw torque and external force are applied; forty physics steps advance one control interval; commands may change; observations/reward/termination are computed; raw action history is stored. Put timestamps beside each event. An observation supplied to the actor must describe the intended decision instant. A reward should be attributable to a defined command and transition, especially around mid-episode setpoint changes.

Finally inspect `_get_obs`, `_compute_reward`, and rendering. Explain each observation and each reward term separately. Rendering must not change commands, noise draws or physics results. `_cmd_yaw_rate` is currently stored but unused. The reward's “diagonal” term actually compares the left motor pair with the right pair. `_get_obs` consumes random noise on every call, so an extra diagnostic call can change subsequent stochastic results; this becomes important when creating reproducible experiments.

**4. Read [nn.c](../../nn.c), [nn.h](../../nn.h), and [weights.h](../../weights.h) together.** The C forward pass is three affine transforms with ReLU after the first two. Read one outer loop as “one output neuron” and one inner loop as “sum the weighted inputs.” Bias is added once. The final layer is linear. Clipping, action filtering and throttle mapping happen in `main.c`, not in `nn_forward`.

Compute the parameter count yourself: `32*12+32 + 32*32+32 + 4*32+4 = 1604`. The weights occupy 6,416 bytes as float32. The action distribution's exploration state and PPO value network are not needed by the deployed deterministic actor. Do not read every weight as if it were an interpretable control gain; test complete network responses and selected local sensitivities instead.

`nn.h` also duplicates the action mapping constants in `weights.h`. Changing an exported constant does not necessarily change every translation unit's interpretation. Map where each macro is seen during compilation, then replace duplication with a shared generated contract in a later implementation pass.

**5. Read [train.py](../../fc-nn/train.py) after understanding the environment and actor.** `POLICY_KWARGS` determines the actor/critic MLPs; `PPO_KWARGS` determines how experience updates parameters. `make_vec_env` creates independent environments wrapped for episode statistics. `SubprocVecEnv` runs workers in separate processes. The checkpoint callback saves periodically; the evaluation callback selects a model from separate evaluation episodes; the metrics callback records episode summaries; the curriculum callback changes task difficulty based on crash history.

Trace one rollout: the stochastic training policy samples actions, workers collect transitions, PPO computes advantages/value targets, minibatches update the policy repeatedly, and callbacks log/save/evaluate. Count the total transitions per update as `n_steps * n_envs`. The archived 11-worker configuration collects 45,056 transitions per rollout. A CLI request for fewer timesteps can still collect a full rollout, so a tiny requested training duration is not a unit test.

Inspect which environment receives each callback update. The curriculum only advances training environments. Inspect what is restored on `--resume`: the model is loaded, but curriculum callback state is newly constructed and the normal `learn` call resets timestep accounting by default. Read [SB3's evaluation guidance](https://stable-baselines3.readthedocs.io/en/v2.7.1/guide/rl_tips.html) for the distinction between training and independent evaluation; retain matched evaluation conditions when comparing changes.

**6. Read [export_weights.py](../../fc-nn/export_weights.py).** Identify how the actor layers are selected, the shapes asserted, tensors converted to float32, and rows serialized. Confirm row-major ordering matches the C loops. Architecture checks are useful, but a future exporter should also verify activation functions, preprocessing and output semantics. A shape-correct network with a changed activation or normalization wrapper could export plausible arrays and compute the wrong policy.

Read [validate.py](../../fc-nn/validate.py) as a test implementation that must itself be reviewed. Its NumPy arithmetic checks one observation against the PyTorch actor, but its displayed PWM uses an obsolete mapping. Its fixed-environment constructor overrides `reset`; compare every omitted state variable to the main environment. Its recovery test only requires one passing sample. Write down what a pass actually proves, rather than copying its final “ready” message into your engineering conclusions.

**7. Read [viewer.py](../../fc-nn/viewer.py) as an interaction layer.** Follow joystick/keyboard → command smoothing → `set_setpoint` → policy call → environment step → rendering. The actor call uses the previously generated observation, so newly updated commands are not reflected until an observation rebuild; decide and document that one-tick command path. Inspect the reset order, persistent input state and commanded altitude. Identify advertised controls that the custom loop actually handles.

The viewer intentionally removes some randomization for visual inspection. Therefore a pleasing viewer flight is a different experiment from randomized training. The recording stride is currently computed using the physics timestep even though the loop runs once per policy tick, producing incorrect video timing. Put `sim_time` on recordings so rendering speed never substitutes for a measurement.

**8. Read [main.c](../../main.c) in startup and control-loop passes.** Startup initializes clock, GPIO/LED, UART, SPI/IMU, motors, AHRS and barometer. It includes calibration/identification behavior and an automatic arming sequence. Draw a state diagram representing actual execution, including which states permit motor commands and how faults leave those states. The current program needs clearer explicit states before it is a sound hardware testing platform.

For the loop, trace a concrete sample: raw IMU counts → axis alignment → unit conversion → startup bias subtraction → AHRS → barometer update → observation construction → NN → clipping → adaptive filter → altitude-adjusted base → throttle ramp → motor index mapping → PWM write → telemetry. Record the difference between source comments, fixed assumed `LOOP_DT`, actual elapsed time and sensor sample age. Inspect early returns/continues: the tilt-stop branch currently falls through to new motor commands.

Your deliverable is a one-page timeline with every persistent variable listed: gyro/accelerometer calibration accumulators, estimator quaternion, barometer state, arming/ramp state, action smoother, tick counters and telemetry counters. Mark precisely when each state resets and whether it survives a fault/re-arm.

**9. Read [ahrs.c](../../ahrs.c) and [ahrs.h](../../ahrs.h) as a stateful estimator.** Begin with quaternion state, initialization, gyro-driven quaternion derivative, accelerometer normalization, gradient correction, quaternion integration/normalization, and Euler conversion. Explain why a gyro gives short-term rotation information while an accelerometer only resembles a gravity-direction measurement when non-gravitational acceleration is limited.

Inspect every division and square root. The exact-rest zero-gradient case presently creates invalid arithmetic in C. Inspect the hardware square-root intrinsic, approximate trigonometry, and error near angle limits. The Python version in `fw_common.py` adds a zero-gradient guard and uses different numeric arithmetic, so agreement must be tested on trajectories, not assumed from similar equations.

**10. Read [baro.c](../../baro.c) and [baro.h](../../baro.h).** Separate transport, chip identification, factory calibration coefficients, raw pressure/temperature compensation, ground-reference estimation, pressure-to-height conversion and vertical-velocity filtering. There are different branches for DPS310 and BMP280. Readiness and successful I²C reads are distinct from a fresh measurement. The update function is called at 100 Hz but internally decimates by four.

Annotate units at every stage: raw ADC integer, coefficient scale, pascals, degrees Celsius, metres and metres/second. The derivative uses an assumed elapsed interval. Ask what happens after a missed measurement, a read failure, or a long UART stall. Independent pressure/height reference data is required to validate the estimator; comparing its output to itself is circular.

**11. Read [imu.c](../../imu.c), [imu.h](../../imu.h), and [spi.c](../../spi.c)/[spi.h](../../spi.h).** Follow device identification, bank selection, reset, full-scale range, output rate, filter configuration, burst read, byte order and signed conversion. The current detected-device branches include ICM42688P, MPU6000 and BMI270; code presence is not evidence all three hardware paths have passed tests.

For the actual installed chip, make a register table containing address, expected raw byte, field decoding and observed readback. The ICM branch sets gyro and accelerometer config values to `0x06` and shared filter register `0x52` to `0x06`; decode all fields using the actual chip's datasheet instead of assuming the macro name fully describes them. SPI bus clock, CPOL/CPHA, chip-select timing and byte ordering should be checked with a logic analyzer. Inspect unbounded polling loops and distinguish transport failure from implausible-but-successfully-read samples.

**12. Read [i2c.c](../../i2c.c)/[i2c.h](../../i2c.h).** Trace bus recovery, peripheral initialization, address probing, register writes, repeated-start burst reads, ACK/NACK and STOP handling. Verify the special last-byte/read-length behavior against the MCU reference manual and a bus capture. Tests should cover one-byte reads, multi-byte reads, absent devices and a stuck bus. A driver that works for one burst length has not necessarily validated every transaction form.

**13. Read [motor.c](../../motor.c)/[motor.h](../../motor.h).** Identify the four pins and timer channels, timer clock, prescaler, auto-reload, compare registers, preload behavior and advanced-timer output enable. Recompute the values: 168 MHz divided by `167+1` gives 1 MHz counter ticks; `2499+1` ticks gives a 2.5 ms frame, or 400 Hz. A command becomes approximately `1000 + 1000*cmd` microseconds. Confirm those quantities on an oscilloscope; successful compilation does not validate a pin's alternate function or the ESC's interpretation.

`motor_all_stop` writes idle pulses. It does not remove electrical power. Motor command, pulse width, rotor speed, thrust and torque are separate physical quantities. Measuring the pulse validates only the first transport step to the actuator.

**14. Read [uart.c](../../uart.c)/[uart.h](../../uart.h).** Follow pin/peripheral selection, baud-rate divisor and blocking transmission. Count telemetry bytes, including delimiters and line endings. At 8N1, each byte occupies ten serial bits. Then find all places that can print inside the control loop. Instrumentation changes the loop being measured unless its runtime and buffering are controlled.

Read [log_imu.py](../../fc-nn/log_imu.py): the PC timestamps received lines, which are not precise IMU acquisition timestamps. Read malformed-line handling, start/duration logic and output schema. Read [analyze_imu.py](../../fc-nn/analyze_imu.py): understand its estimated sample rate, statistics and spectra, and the exact columns required. The old static CSV has a different schema. Existing PNGs are historical outputs; regenerate only from an explicitly identified compatible input file.

**15. Read [clock.c](../../clock.c)/[clock.h](../../clock.h), [startup.c](../../startup.c), [linker.ld](../../linker.ld), and [memset.c](../../memset.c) last in this conceptual pass.** The clock code establishes the timing assumptions used throughout the project. Startup copies initialized data from flash to RAM, clears zero-initialized storage, enables the FPU and calls `main`. The vector table chooses exception handlers; default handlers loop. The linker script describes flash/RAM/CCM placement and the initial stack. `memset.c` supplies a freestanding runtime helper.

Then revisit these files first in actual power-on order. Check symbol addresses, section alignment, vector-table retention, memory usage, initialization of every writable section and behavior after unexpected interrupts. Test a known initialized global, a zero-initialized global and a simple FPU computation on a bench-only firmware. If future code uses CCM, establish its initialization policy; defining a linker section alone does not initialize its contents. Keep stack margin distinct from the linker-reported static BSS total.

**16. Read [Makefile](../../Makefile) as part of the controller's provenance.** Identify the normal and test source lists, CPU/FPU ABI flags, freestanding link, garbage collection, compile-time modes, binary conversion and flashing commands. Run a dry build to see exact commands. Notice source-only dependencies miss headers and linker changes, and changing flags does not invalidate outputs. A wrong stale binary is a system-level bug even when every C function is correct.

**17. Read the tests with the same skepticism as production code.** `test_nn_parity.py` compares exported tensors and writes reference vectors; `host_test/test_nn_host.c` runs actual inference plus copied filter/mixer diagnostics; `test_env_physics.py` bypasses policy to test plant behavior; `fw_common.py` provides separate Python controller/estimator implementations; `test_firmware_sim.py` couples those copies to a plant. The 3,527-line `test_harness.c` contains hardware-oriented experiments. Its test 7 uses real sensors with motors off; it is not a plant feeding back from real commanded motion. Later motor tests run automatically in the present sequence.

For each test, write its stimulus, observed variable, expected result, tolerance and failure implication. Identify anything it does not cover. A test of two Python functions that share the same mistaken constant cannot establish physical truth. A C-vs-Python arithmetic match cannot establish stable flight. A 30-second survival count cannot establish position hold.

**18. Finish by explaining the artifact files.** ZIPs contain learned policy state and metadata, not the complete historical environment. `weights_working_w_pulse.h` is a second exported actor. TensorBoard event files record metrics but do not preserve every training setting or sensor model. ELF files include linked executable/debug information; BIN files are flash payloads. CSVs contain measurements; PNGs contain derived visualizations. `.venv` is a local dependency installation, not a reproducible dependency specification. `.DS_Store` and generated bytecode are not engineering evidence.

You understand this pass when you can trace one observed oscillation to the exact files that could cause it, reproduce the code's units and timing on paper, and name an experiment that separates those causes. You do not need to memorize register addresses or individual neural weights.
